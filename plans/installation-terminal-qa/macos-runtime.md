# Native macOS runtime and Homebrew QA, 2026-10-27

The goal was to stop macOS XProtect from trashing CodeLima while retaining its terminal emulator and real Lima VM behavior. The 1.0.1 candidate passed native VZ, terminal rendering, live handoff, renderer recovery, and local Homebrew package checks. Its ad hoc signing does not qualify it for an ordinary downloaded Gatekeeper launch.

The host was an Apple M4 Max arm64 Mac running macOS 26.6.2 with 16 CPUs and 64 GiB RAM. Lima 2.2.1 and Homebrew CodeLima 1.0.0 were already installed. All runtime work used `tmp/macqa/h` and `tmp/macqa/l`, with a separate mounted workspace and a custom shell profile. Host-auth import was disabled. The existing CodeLima home and daemon were not used. At baseline, `command -v codelima` was empty even though Homebrew recorded 1.0.0 installed. This test did not repair that existing keg.

The tested archive was `tmp/codelima-repair/mac-package/dist/codelima_1.0.1_darwin_arm64.tar.gz`. Its SHA-256 was `f4a6714462941dc096276cf2c47c2bfc5c95055a5326668860af2531487bd3a2`, exactly matching its manifest. The renderer build ID in that manifest was `71bf404f8734c63cf06c42a9d0589e21bf74e9bfff2f518327e6771eaf1b77c2`.

The coordinator's `xprotect-results.json` records no matches for either exact candidate binary under the host XProtect rules. Its v1.0.0 positive control matches `XProtect_MACOS_FRIENDLYFERRET_SECD`. This runtime slice verified the scanned hashes and launched the candidate and installed pair. It did not independently establish that every Apple malware subsystem or future rule update will accept them.

`spctl --status` reported assessments enabled. `spctl --assess --type execute` rejected both isolated binary copies. `codesign --verify --strict` accepted their embedded signatures, while display showed ad hoc linker signing and no TeamIdentifier. A separate copy with an explicit quarantine attribute did not return `--version` within 60 seconds and was terminated. It produced no successful version output. No Gatekeeper, quarantine, or XProtect setting was disabled, and no Developer ID or notarization claim follows from these results.

One cleanup error affected pre-existing Homebrew state. Uninstalling the disposable formula also autoremoved `docker-completion` 29.9.2. `HOMEBREW_NO_INSTALL_CLEANUP=1` does not disable autoremove. The exact 29.9.2 bottle was restored with auto-update, install cleanup, and autoremove disabled. `brew tab --no-installed-on-request` restored its autoremove eligibility, which the removal demonstrated it previously had. The complete installed formula/version list then exactly matched the baseline. Reinstallation changed its installation timestamp and receipt metadata. There was no pre-image for exact byte restoration. Future disposable Homebrew checks must set `HOMEBREW_NO_AUTOREMOVE=1` from the start.

Cleanup removed the owned VZ instance, daemon, three shells/transports, renderer workers, TUI processes, inputrc temporary file, unique keg, tap, formula lock, isolated trust store, caches, copied quarantined binaries, workspace, diagnostic bundle, captures, and all `tmp/macqa` scratch files. Homebrew's test command had installed eleven Ruby gems into its vendor bundle and created `~/.bundle`; their new files, native extension, wrapper executables, and cache were identified by the install log and creation times and removed. Developer mode returned to disabled. Lima reused its pre-existing image cache and created no new download-cache files. The existing CodeLima keg, tap, default home, and default daemon were not changed by this slice.

Prove It Works changed the checks from text alone to actual cell attributes, exact binary hashes, live process IDs, and native VZ behavior. Sequence Work into Verifiable Units changed cleanup into separate runtime, package, and baseline-state comparisons. The baseline comparison caught the Homebrew autoremove error before completion. The raw verification artifacts were cleaned as required. This report and the coordinator-owned candidate, manifest, and scanner evidence remain.
