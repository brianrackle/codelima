# Codebase review: codelima

**TLDR:** The codebase is far healthier than the README's "100% vibe-coded" disclaimer suggests — lint is fully clean, CI runs verify + race on two OSes, the atomic-write primitive is textbook, rollback discipline in node lifecycle is genuinely careful, and the actor-ownership patterns in the TUI and emulator are sound. But the daemon hangs and intermittent performance issues you already know about are not mysteries: this review found specific, verified mechanisms for both. The two systemic problems are **(1) blocking work held in the wrong places** — global file locks held across multi-minute VM operations, and the TUI event loop performing synchronous RPCs and lock acquisitions — and **(2) state duplicated across processes and reconciled by 1-second polling and full-grid snapshot pulls** instead of a single event-driven source of truth.

I reviewed all five subsystems (daemon, TUI, renderer/cgo, service/Lima, persistence/config/CLI) with parallel deep-read passes, then independently verified every critical claim below against the source.

## 1. Why it hangs — the stall mechanisms

These findings interlock into a coherent explanation of the "daemon hangs" symptom. Each is independently verifiable at the cited lines.

**1a. Global flocks are held across multi-minute VM operations.** `NodeStart` acquires the global `nodes` flock (`service.go:849`) and holds it through VM boot (15-minute limactl budget), workspace seeding, every bootstrap command (apt/npm installs), and agent validation — worst case over an hour. `NodeCreate` and `NodeClone` are similar. Meanwhile `seedAndRepair` takes **all three** lock domains on every mutating command *and on TUI/daemon startup* (`service.go:307`). So while any node is booting, launching the TUI blocks. And `flockWithContext` (`locks.go:67-82`) polls forever with no timeout and no "waiting for lock" log — the block is silent and indefinite. **Fix:** hold locks only for metadata read-modify-write; use a `provisioning` status field as the concurrency guard during the VM work; add per-node locks so independent nodes parallelize (the tool's whole purpose is multiple sandboxes, and today one lifecycle op serializes the system); check the seed-version stamp before locking in `seedAndRepair`; log after ~1s of lock waiting.

**1b. The TUI event loop performs blocking work.** Dialog submits run `Service.Configuration*`/`Environment*` calls synchronously inside the event loop (`tui_dialogs.go:244` etc. via `tui_overlay.go:184-198`) — which acquire those same flocks with the app-lifetime context. If the daemon or a CLI holds the lock, pressing Enter freezes the whole TUI unrecoverably (raw mode swallows Ctrl+C). Also on the loop: `terminal.open` RPC (5s timeout) fired on *every selection move onto a running node* (`tui_input.go:113-131`), `terminal.resize` RPC inside `Draw()` that **retries every frame on failure** (`tui_terminal_daemon.go:85-99` — a degraded daemon turns every redraw into a 2s stall), `input.takeover` on every window focus change, and terminal teardown that waits out a SIGHUP→SIGTERM→SIGKILL escalation (~4.5s per tab, sequential on quit). **Fix:** the loop must never block — route all of these through the existing `startOperation` background pattern or fire-and-forget queues with results applied via posted events.

**1c. The event queue is lossy exactly when it matters.** vaxis `PostEvent` silently drops events when its 1024-slot queue is full — i.e., precisely when the loop is stalled per 1b while 20Hz redraw events stream in. Three one-shot events are load-bearing latches: `tuiRefreshCompleteEvent` (dropped → auto-refresh dies silently), `tuiOperationCompleteEvent` (dropped → "operation already in progress" forever), and `tuiDaemonSynchronizedEvent` (dropped → the reconnect supervisor blocks permanently at `tui_sessions.go:184-191` and every terminal RPC fails with "daemon connection is synchronizing" until restart). **Fix:** use `PostEventBlocking` or dedicated channels for completion/handshake events, and make the latches self-healing with timeouts.

**1d. The daemon serializes keystrokes behind slow control operations.** Each connection has one serial mutation lane (`daemon/server.go:514-547`): `terminal.send_event` shares it with `terminal.open`, `terminal.close` (up to ~5s of signal escalation), and `daemon.update` (minutes). The TUI sends everything over one shared client, so closing a tab with a TERM-immune shell freezes input to *every* tab; 64 queued mutations kill the connection entirely. **Fix:** give input events their own ordered lane; run slow teardown asynchronously after replying. Use the delivery-class taxonomy already written down in STABILITY_PLAN.md: input (at-most-once, ordered) keeps the serial lane; resize/focus are replaceable latest-value state (coalesce, reassert); open/close/update dispatch concurrently — their ordering is already protected by `h.mu` — with slow teardown finishing after the reply.

**1e. Daemon-dispatched `node.start` is killed at 30 seconds.** The server is constructed without `RequestTimeout` (`daemon_host.go:959`), so the 30s default (`daemon/server.go:117-118`) wraps every request (`server.go:550`), including node lifecycle that legitimately takes minutes. At 30s the context cancels, the limactl process group is SIGKILLed mid-boot, and the node is persisted as `Failed`. Also, `node.start`/`node.stop` aren't in `mutatingInputMethod`, bypassing the ownership gate. **Fix:** per-method timeout classes, or run lifecycle as daemon-side background jobs streaming progress events.

**1f. A renderer that exhausts its restart budget permanently freezes the shell.** After 5 restarts/minute, `restart()` sets `link = nil`, publishes "degraded," and nothing ever re-arms it (`renderer_supervisor.go:377-385`). `SendOutput` then waits forever on `s.ready.Wait()` for a condition that can never become true (`renderer_supervisor.go:198-212`), wedging the PTY read pump; the kernel PTY buffer fills and the shell blocks on write with **no error surfaced**. Compounding it: every restart replays the whole journal (up to 1 MiB) inside a fixed 2s init deadline with 0–100ms backoff, so a poison journal burns all five attempts in about a second, with no truncated-journal retry. **Fix:** in degraded state return an error from `SendOutput` (the journal already holds the bytes), retry restarts on a ~30s cooldown, scale the init deadline with journal size, and retry once with a cleared journal before giving up. This is the restart policy STABILITY_PLAN.md specified but the implementation dropped: the budget resets after a sustained healthy period, degraded means stale-but-alive (input rejected with an error, journal still absorbing, last snapshot visible), and a manual renderer restart stays available.

## 2. Why it's intermittently slow — the performance mechanisms

**2a. VirtioFS reclaim: drop the threshold trigger, run on a fixed 60-second cadence.** *(Correction: reclaim is not a source of slowness. It exists to work around an Apple Virtualization VirtioFS bug and should simply run periodically.)* Today it only fires when host-wide `kern.num_files / kern.maxfiles` crosses a 20% threshold (`host_file_pressure_darwin.go:8-18`, `config.go:57-58`), with a 30s cooldown — meaning whether the workaround runs at all depends on unrelated host activity. **Fix:** remove the host file-table sampling, the threshold setting, and the cooldown logic entirely; while enabled, run `echo 2 > /proc/sys/vm/drop_caches` in every running mounted node on a plain 60-second timer. This deletes the darwin sysctl sampler and the `VirtioFSReclaimThresholdPercent` settings surface (keep the on/off switch), simplifies `virtioFSPressureController` to a ticker, and makes the workaround deterministic. Update SPEC.md's daemon-settings section (which currently specifies the 1–95% threshold) to match.

**2b. The terminal snapshot pipeline does full-grid JSON at up to 20 Hz.** Per publish: five separate worker round-trips, up to 2×2000 scrollback rows fetched **one cgo call per line**, every cell serialized as a ~15-key JSON object (a 160×50 grid ≈ 2–3 MB), unmarshaled, then cloned twice more — and on the daemon side the identical snapshot is **re-marshaled per client per pull** (`daemon/server.go:861-868`), with `ReadVisible`/`ReadRecent` variants recomputed on every wake even when nothing calls `terminal.read`. Additionally the supervisor deep-copies the entire journal on *every inbound frame* for status publication (`renderer_supervisor.go:290` → `journal.Snapshot()`), ~20 MiB/s of memcpy under the mutex contending with the PTY hot path. **Fix (in order of payoff):** cache marshaled snapshot bytes and reuse across clients; compute read variants and status stats lazily (`journal.Stats()` returning two ints); compact JSON tags or a binary cell encoding; longer-term, dirty-row deltas — the `GhosttyDirty` value already exists and every caller discards it. The target encoding is the split STABILITY_PLAN.md prescribes (§4.5 of its final document): JSON for control frames only; a fixed binary frame header with raw bytes for PTY output and snapshot payloads; snapshots chunked (`SnapshotBegin/Chunk/End`) so large grids don't fight the 1 MiB frame cap.

**2c. 1-second polling everywhere, on top of a working push system.** The daemon forwarder calls `NodeList` every second, re-reading and re-YAML-parsing every node + configuration file from disk; the TUI *also* polls `node.list` every second even though the daemon pushes `node.status_changed` events; in no-daemon mode the TUI spawns `sh -lc "limactl list --json"` — a login shell plus limactl — every second. Every event also triggers a full-screen rebuild with no coalescing of queued redraws (`tui_render.go:557-664`). **Fix:** mtime-keyed metadata cache in Store; forwarder consumes the observer cache instead of full `NodeList`; event-driven TUI refresh with a slow fallback poll; drain and collapse consecutive Redraw events before drawing.

**2d. Forwarder reconcile is sequential.** One unreachable node (booting, post-sleep) adds up to ~20s during which every other node's port discovery and telemetry is frozen, with warn-log spam on every retry forever (`dynamic_forwarding.go:442-467`). **Fix:** bounded per-node worker fan-out with per-node backoff.

**2e. Renderer items STABILITY_PLAN.md called for that were never executed.** (1) *Per-process stderr redirection:* renderers are now isolated processes, yet every libghostty bridge call still takes a process-global mutex plus four dup/dup2 syscalls (`tui_terminal_ghostty_cgo.go:68-114`) — in the in-process TUI backend this serializes all terminals' emulation, reads, and input on one lock. Redirect fd 2 once at process startup (trivially correct in the worker, which owns exactly one terminal) and delete the per-call wrapper. (2) *Resize-event coalescing in the journal:* resize events are never trimmed or charged bytes (`renderer_journal.go:53-60`), so a window-drag storm bloats every replay inside the fixed init deadline (compounding 1f); coalesce consecutive resizes and charge them a nominal byte cost.

## 3. Correctness and data-integrity risks

- **Concurrent map write during live update (crash).** `importDaemon` populates `host.terminals`/`terminalOrder` with no lock (`daemon_host.go:1417-1423`) while renderer supervisors started earlier are already delivering callbacks that read the same map under `RLock`; `host.broadcast` is likewise assigned unsynchronized after publisher goroutines can read it. This is a fatal-runtime-panic race sitting on every live update. Take `h.mu` around adoption, and wire broadcast/stop functions before creating entries.
- **Live update clobbers `session.json` with an empty terminal list.** `update()` deletes handed-off terminals, then the old daemon's `Close` persists — writing empty recovery intent (`daemon_host.go:714-718, 1258-1268`) that the new daemon never rewrites until some later mutation. A crash in that window loses every tab, defeating session.json's purpose. Persist in `importDaemon` before signaling commit, and skip persist-on-close once replaced.
- **`settings.yaml` refresh silently wipes user settings.** The loader unmarshals the whole `Config` (so fields like `default_image`, `runtime_commands` work), but the refresh writer serializes *only* the daemon block and rewrites the file whenever a new daemon key ships (`config.go:79-95`, `runtime_commands.go:114-145`). Reader and writer must agree; round-trip unknown fields via `yaml.Node`.
- **Login-shell transport corrupts limactl JSON parsing tool-wide.** Every runtime command — including `limactl list --json` — runs as `sh -lc` (`lima.go:745`), sourcing `/etc/profile` and `~/.profile` per invocation. Any profile that prints to stdout breaks `parseLimaList` → `MetadataCorruption` → NodeList, the forwarder loop, and preflight checks all fail. A `runDirect` argv path already exists; use it for built-in commands, or drop `-l`.
- **Shell-injection/quoting bug in the root guest shell.** `fmt.Sprintf("cd %q && %s", workdir, ...)` (`service.go:1541`) uses Go quoting, which does not escape `$` or backticks — a node directory containing `$(...)` executes as root in the guest. The correct `shellQuote` helper exists in the same package and is used for the adjacent seeding path.
- **One corrupt file bricks the tool; logs break permanently.** `ListNodes` aborts on the first malformed `node.yaml` (`store.go:620-653`), and the TUI/daemon/doctor all route through it — one bad record makes everything unusable with no quarantine or `doctor --repair` path. Similarly `readEvents` fails forever on one torn/oversized line (`events.go:18-72`, default 64KB scanner limit; the Lima parser got an enlarged buffer, the events reader didn't). List paths should skip-and-warn; doctor should quarantine.
- **Cross-platform build clobbering and a broken Homebrew install** *(both fixed 2026-08-03)*. The repo is mounted host+guest at the same path, and every `make build` on either side rewrote the shared `bin/codelima` symlink to its own platform's ELF/Mach-O — flipping the host's entry point to a wrong-architecture binary (the `nodeTabStartError` ENOEXEC message existed precisely for this) — and `make clean` deleted *both* platforms' binaries. Fixed: `bin/codelima` is now a platform-dispatching script installed from `scripts/codelima_dispatch.sh`, `clean` is scoped to the current platform (`clean-all` for the full wipe), and `package_release.sh` no longer rewrites the compat path. Separately, the Homebrew formula installed only `codelima-real` into `libexec/bin` while the runtime resolves `codelima-renderer-worker` strictly beside the running executable (`renderer_supervisor.go:580-598`) — every brew-installed daemon terminal would have failed to start its renderer. Fixed in the formula template (`internal/release/release.go`): the worker is installed beside `codelima-real`, guarded by an `odie`, and asserted in `test do`; ships with the next tagged release.
- **Observer cache staleness feeds mutating decisions.** During a healthy `limactl watch` (days), the cache is never resynced; event-synthesized entries lack SSH config; a failed initial list still marks the cache authoritative; and daemon-side `NodeStart` consults it to decide whether to actually start the VM (`lima_observer.go:47-126`, `service.go:865-878`). Add periodic reconciliation and bypass the cache for mutating decisions.
- **Smaller but real:** broadcast increments the event revision before marshal can fail, forcing sequence-gap reconnect storms (`daemon/server.go:298-320`); `NodeClone`'s deferred source-VM restart reuses the possibly-cancelled caller context so Ctrl+C leaves your VM stopped (`service.go:1094-1113` — the nearby rollbacks already use fresh contexts); `SaveNode`'s six-file write has crash windows that can re-run bootstrap (`store.go:474-516`); a `.DS_Store` in a fresh `~/.codelima` makes first-run fail "unrecognized home layout" (`store.go:92-113`) — on a macOS-first tool; fixed 10-minute cap on all guest commands kills slow bootstraps and marks nodes Failed (`lima.go:671`); one unknown limactl status string fails the entire list parse and Lima 3.x is rejected outright (`lima.go:140-158, 231-247`); the ghostty key-encoder retry checks `OUT_OF_MEMORY` where the contract returns `OUT_OF_SPACE` (`tui_terminal_ghostty_cgo.go:715` — the sibling paths at 637/781 check the right code); the C viewport fill lacks per-write bounds checks against a dlopen'd library that can skew versions (`ghostty_bridge_compat.c:736-778`); daemon.log never rotates while the TUI log does; the TUI event-stream read deadline equals the daemon heartbeat interval (2s vs 2s — `tui_sessions.go:118`, `daemon/server.go:132-134`), leaving zero slack, so a briefly busy daemon triggers routine timeouts and full-resync storms — set the deadline to 2–3× the heartbeat interval (STABILITY_PLAN.md's 10s-ping/30s-dead guidance had the right proportions).

## 4. Design and maintainability

**The single mega-package is the root maintainability issue.** 102 files / ~40k lines in `internal/codelima` spanning CLI, TUI, daemon host, renderer, Lima client, and store — no compiler-enforced layering, so anything can reach anything (and does: the forwarder holds a `*Service` just to enumerate running instances; `Service` is 1,773 lines plus more files extending the same type). The extracted `daemon/` and `daemonclient/` packages prove the seams work. A realistic target: `store`, `lima` (client + observer), `service`, `forward`, `renderer`, `tui`, with the existing typed-error and event contracts as boundaries. This would also force fixes for the upward dependencies (finding 15 in the service review: extract a narrow "runtime inventory" interface for the forwarder).

**State lives in three-plus places reconciled by polling.** Store YAML, observer cache, forwarder maps, plus TUI-side mirrors of daemon-owned truth (tab lists reconciled only at reconnect — another TUI window's new tab is invisible until a reconnect because `target.tabs_changed` only triggers a repaint of stale state). Converging on "daemon owns truth, pushes typed events, everyone else caches" would eliminate most staleness bugs and most of the polling cost in one design move.

**Protocol/API hygiene:** daemon events are stringly typed with `map[string]any` decoding duplicated in three places; the mutating-method list is hand-duplicated between client and server (`daemonclient/client.go:584` vs `daemon/server.go:818`) where drift silently bypasses input-ownership checks; the renderer worker protocol has **no version field** at all, so on-disk binary skew after an upgrade is silently misinterpreted rather than rejected; supervisor `Try*` methods actually block. The TUI reflects into unexported vaxis internals on the mouse hot path, degrading silently to wrong input semantics if vaxis changes (canary tests only catch it at test time).

**Tests:** coverage is strong on protocol/queue/reconnect mechanics and store seeding, but `GO_TEST_PARALLEL=1` forces fully serial runs (an isolation smell), CI never runs `make test-integration` (daemon lifecycle untested in CI), `make verify`'s `fmt` step rewrites files and exits 0 so formatting can't fail CI, and there is **zero coverage of the locking layer, the events log, or any of the hang class** — no slow/hung-daemon fake, no dropped-event injection, no flock contention test. The 4.5k-line `tui_test.go` monolith and post-migration characterization pins are worth splitting/retiring. Fault-injection tests should land *with* the fixes in section 1 to lock in "the loop never blocks" as an invariant (the concrete owed-test list is in §5).

**Docs/hygiene (small):** SPEC.md drifted from code (the retired `default` configuration slug, missing `context.jsonl`/by-slug index in the storage layout); ROADMAP.md links plans by absolute paths under `/Users/brianrackle/personal/...` that don't exist in this checkout; two error strings say `config.yaml` for what is `settings.yaml`; two empty `cmd/codelima-microsandbox-*` remnants; duplicated `cloneMap`/`cloneStringMap`; test-only dispatch shims in production files.

## 5. Stability invariants (adopted from plans/STABILITY_PLAN.md)

STABILITY_PLAN.md is three stitched design reviews; most of its architecture already shipped (reconnect supervisor, close-cause records, bounded per-client pumps, immutable snapshot caches, per-terminal renderer processes — ADRs 107–108, 112–115). What remains valuable are its **invariants** — several of which the implementation states but currently violates — and the work items now folded into §1–§2 above. Adopt these as acceptance criteria for the hang work:

- **I1. The TUI event loop never performs blocking work** — no socket I/O, no RPCs, no flocks, no process teardown. The plan stated this for sockets; the RPC/flock/teardown paths violate its spirit. (Findings 1b.)
- **I2. No latched failure states; only explicit shutdown stops recovery.** Every "in progress" / "synchronizing" / "degraded" state must be self-healing — timeout, retry, or state re-derivable on the next render — never dependent on a one-shot event arriving. (Findings 1c, 1f.)
- **I3. A connection is a transport boundary, not a serialization boundary.** A slow control operation must never delay input delivery or another terminal's requests. Enforced via the delivery-class taxonomy in 1d. (Finding 1d.)
- **I4. The PTY read pump never waits on the renderer.** Degraded means stale-but-alive: the journal keeps absorbing, input is rejected with a visible error, restart stays reachable. (Finding 1f.)
- **I5. Liveness deadlines carry slack.** Any read deadline on a heartbeat-bearing stream is ≥2–3× the heartbeat interval. (§3 heartbeat item.)
- **I6. Forwarding state degrades before it disappears.** Routes are torn down only on a confirmed node stop/delete (explicit event or a confirming direct `limactl list`) — never inferred from a single failed scan, a failed `NodeList`, or a stale cache read. When a port's routes lapse transiently, the host listener stays bound and serves 502 (retryable) rather than closing (connection refused, which clients cache). (§6 findings.)

**Acceptance bar** (STABILITY_PLAN Phase 0): the next captured freeze must yield a one-line causal diagnosis from the existing close-cause records — e.g. "connection N closed at T: outbound queue full for 5s; client reader stalled" — not just a broken-pipe symptom.

**Fault tests still owed** (named in STABILITY_PLAN, absent from the suite): restart-budget exhaustion / degraded-state behavior; SIGKILL'd renderer worker (the current test only covers a cooperative hang); partial/split protocol frames; a `SIGSTOP`'d TUI client; host sleep/resume; "a slow mutation does not stall same-connection input"; session.json integrity across live update. Forwarding (I6): dead-peer detection via keepalive loss; routes survive a transient scan failure inside the grace window; teardown happens only on confirmed stop; the listener answers 502 (not refused) while routes lapse.

**Superseded:** STABILITY_PLAN's final document (cgo-free daemon + per-terminal *session workers* + three binaries) contradicts the two documents above it and the shipped architecture; there is still no evidence the pure-Go PTY actor destabilizes the daemon, which was that document's own bar for the split. Session workers, PTY escrow, and daemon-crash worker adoption stay deferred. From that document, only the restart policy (folded into 1f), the control/data encoding split (folded into 2b), and its Unix edge-case table remain live references.

## 6. Dynamic forwarding — why `localhost:{port}` stops reaching the VM

Verified against `dynamic_forwarding.go` and `lima_ssh.go` after reviewing plans/DYNAMIC_PORT_FORWARDING_SPEC.md. The spec's routing model (Host-header routing, generic claimant, node hostnames) is sound and the implementation follows it; every failure mode below lives in resilience territory the spec never specifies.

**6a. Route teardown is coupled to a fragile combined scan.** Discovery is not the spec's `cat /proc/net/tcp` — it's one combined SSH command that also samples CPU, meminfo, and `df` (`dynamic_forwarding.go:78-81`) under a 10s timeout, once per second. Two consecutive failures (`handleDiscoveryFailure`, `dynamic_forwarding.go:474-492`) delete the peer **and all the node's routes**, which closes the port's host listener — `localhost:{port}` goes 502 → **connection refused**. A guest under heavy agent load (compiles, fork pressure) can miss the 10s budget twice; host sleep/wake does it reliably. **Fix:** split the ports scan from telemetry; on scan failure keep routes through a ~15s grace window; per I6, keep the listener bound serving 502 while routes lapse.

**6b. Dead SSH peers are never detected proactively, and proxied dials hang unboundedly.** Nothing sends keepalives after the handshake (`lima_ssh.go:81-87` clears the deadline and no ping loop exists), and the route transport's dial is bounded only by the browser's patience (`dynamic_forwarding.go:96-118, 282`). After sleep/wake the peer is dead-but-not-closed: requests hang, then 502, then refused once 6a's two-strike fires ~20s later. **Fix:** `keepalive@openssh.com` every ~5s with 2–3 missed → proactive reconnect; a ~5s dial timeout on the proxy path so requests fail fast.

**6c. One `NodeList` error halts all reconciliation, silently.** `reconcile` returns on any `NodeList` failure (`dynamic_forwarding.go:403-407`) — every second, forever, logged only to daemon.log. The §3 failure modes (one corrupt `node.yaml`, `sh -lc` profile output corrupting `limactl list --json`, an unknown status string) freeze the route table: dead peers are never replaced, new dev servers never discovered. **Fix:** on `NodeList` failure keep maintaining existing peers and surface the condition in the TUI; the underlying fragility is §3's quarantine/`runDirect` work.

**6d. The observer cache alone decides "running", and the not-running path is a one-strike route killer.** Reconcile trusts `LastRuntimeObservation.Status` (`dynamic_forwarding.go:410`) and *immediately* closes peers and routes for anything else (`dynamic_forwarding.go:421-432`) — no two-strike grace like discovery has. Watch-synthesized cache entries lack `SSHConfigFile`, so `ForwardingSSHConfig` fails with `metadataCorruption` (`lima_ssh.go:35-37`) and that node can **never** get routes until a full cache resync (which only happens on watch failure); a failed initial list serves an empty-but-authoritative cache that yanks every route in one tick. This is the strongest candidate for "VM clearly running, localhost persistently dead." **Fix:** teardown only on confirmed stop (I6), the same grace for the not-running path, and §3's observer-cache reconciliation.

**6e. Generic-claimant migration is permanent.** When two nodes share a port and your node's routes blink once (6a/6d), the generic claim transfers — and never returns, because re-discovery assigns a fresh `DiscoveredAt` so the other node stays "earliest" (`firstClaimantLocked`, `dynamic_forwarding.go:685-700`). `localhost:{port}` then reaches the *other* VM until it stops; only `{node}.localhost:{port}` reaches yours. **Fix:** sticky claimant (prefer the previous claimant when it reappears within a window) and surface the current claimant in the TUI, not just `daemon snapshot`.

**6f. Smaller reachability gaps.** A literal `http://[::1]:{port}` gets HTTP 421 — the generic-host check accepts only `localhost` and `127.0.0.1` (`dynamic_forwarding.go:745-748`) even though the `::1` listener is bound; widen it to loopback literals. Guest servers bound to a specific interface IP (`--host 192.168.x.x`) or inside a container netns with Docker's userland-proxy disabled are invisible to the root-netns `/proc` scan (`dynamic_forwarding.go:237-248`), and ports <1024 are excluded — document these limits where users will see them. Non-HTTP protocols (TLS dev servers, databases, prior-knowledge h2c/gRPC) accept the TCP connection and then break at the HTTP proxy — document HTTP/WebSocket-only prominently. And forwarding exists only while the daemon is healthy: §1's hang modes take it down too, and live update has a deliberate dead window (spec §9) that the §3 `importDaemon` bugs can extend indefinitely.

**6g. The spec document itself is stale.** DYNAMIC_PORT_FORWARDING_SPEC.md §2/§4.2/§7/§14 still specify the Microsandbox transport (`msb ssh serve --stdio`, SDK 0.6.6, per-home key authorization) that ADR 92 replaced with Lima's per-instance SSH config; §6's discovery command and §11's snapshot shape drifted too. Rewrite it around the Lima transport and add the resilience contract above (peer health, `NodeList`-failure semantics, per-node concurrent reconcile per 2d, listener-persistence semantics) so the next implementation pass has something to be held to.

Diagnosis aid while any of this is unfixed: during an incident, `codelima daemon snapshot` distinguishes the scenarios — `last_error` (6c), the port's `status` serving/conflicted (6a), route present vs absent (6d/6f), `default_node` for the claimant (6e).

## 7. What I'd fix first

Ordered by user-visible-pain per unit of effort:

1. **Never block the TUI event loop** (1b) + reliable completion events (1c) — this alone likely kills most perceived freezes.
2. **Shrink flock critical sections; per-node locks** (1a) — unblocks parallel node ops and TUI startup.
3. **`RequestTimeout` class for lifecycle RPCs** (1e) and **input lane separation in the daemon** (1d).
4. **Renderer degraded-state escape + journal-aware init deadline** (1f) — eliminates the silent frozen-shell mode.
5. **Forwarding resilience** (§6) — SSH keepalives + bounded proxy dial (6b), scan/telemetry split with a grace window (6a), listener persistence and teardown-only-on-confirmed-stop (6d, I6): ends the "localhost stopped reaching the VM" class. Fold in 2d's per-node fan-out while in the file.
6. **VirtioFS reclaim cadence** (2a) — delete the threshold/pressure machinery and run the Apple-VirtioFS-bug workaround on an unconditional 60-second timer.
7. **Drop `-l` from the command transport / use `runDirect`** (§3) and the `%q`→`shellQuote` fix — both tiny, both eliminate whole failure classes (and unblock 6c).
8. **Snapshot pipeline economics** (2b) plus the two never-executed renderer items (2e — startup stderr redirect, resize coalescing): cached marshal + lazy read variants + `journal.Stats()` are each small, high-yield patches; the binary encoding split and delta encoding can come later.
9. **importDaemon locking + session persistence ordering** (§3) — the live-update path is the most intricate state machine in the system and currently has both a crash race and a data-loss window.
